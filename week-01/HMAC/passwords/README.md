# Безопасное хранение паролей на Go: от plaintext до pepper

Учебный AppSec-проект. Он показывает, как шаг за шагом превратить уязвимую регистрацию с паролями в открытом виде в схему хранения по современным рекомендациям: **Argon2id + случайная соль + pepper (HMAC-SHA256)**.

Каждая папка — отдельный этап. Код в них можно сравнивать, чтобы увидеть, какая уязвимость закрывается на каждом шаге и как именно.

> ⚠️ **Проект учебный.** Первые этапы уязвимы намеренно. Не используй их код в реальных приложениях.

---

## Стек

- **Go** — стандартная библиотека `net/http`, `database/sql`, `crypto/*`
- **SQLite** — драйвер [`modernc.org/sqlite`](https://pkg.go.dev/modernc.org/sqlite) (чистый Go, без CGO)
- **Argon2id** — [`golang.org/x/crypto/argon2`](https://pkg.go.dev/golang.org/x/crypto/argon2)

## Этапы

### Этап 1. `typicalVulnSite`: пароли в открытом виде

**Что сделано:** HTML-форма регистрации, HTTP-сервер на Go и сохранение пользователей в SQLite.

**Уязвимость:** пароль сохраняется в базу как есть.

```
1|ivan|qwerty123
2|maria|MySecretPass!
```

Любая утечка базы (SQL-инъекция, украденный бэкап, недобросовестный администратор) сразу раскрывает пароли всех пользователей. Люди часто используют одни и те же пароли, поэтому под угрозой оказываются и их аккаунты на других сайтах.

**Меры защиты, применённые уже на этом этапе:**

| Мера | Зачем |
|---|---|
| Параметризованные SQL-запросы (`?`) | защита от **SQL-инъекций**: ввод пользователя никогда не становится частью SQL-кода |
| Валидация на сервере (длина пароля ≥ 8 символов, через `utf8.RuneCountInString`) | атрибут `minlength` в HTML легко обойти через `curl` |
| `Content-Type: text/plain` в ответах с пользовательскими данными | браузер не интерпретирует логин вида `<script>` как HTML (**XSS**) |
| Общие сообщения об ошибках («Внутренняя ошибка сервера») | ошибки БД не раскрывают структуру таблиц и запросов (**information disclosure**) |
| `UNIQUE` на колонке `username` | нельзя создать два аккаунта с одним логином |

### Этап 2. `slowHashFunction`: медленный хеш Argon2id

**Что сделано:** вместо пароля в базе хранится его хеш, вычисленный через **Argon2id**.

```go
argon2.IDKey(password, salt, 3, 64*1024, 4, 32)
//                          t   m (64 МБ) p  длина
```

**Почему Argon2id, а не SHA-256 или MD5:**
- MD5 и SHA-1 криптографически сломаны;
- SHA-256 надёжен, но **быстрый**: видеокарта перебирает миллиарды вариантов в секунду;
- Argon2id специально сделан **медленным и требовательным к памяти** (memory-hard): один хеш считается около 100 мс и занимает 64 МБ RAM, поэтому массовый перебор на GPU и ASIC становится очень дорогим. Это рекомендация OWASP номер один и стандарт RFC 9106.

**Оставшаяся уязвимость (намеренно):** у всех пользователей **одна и та же соль**. Одинаковые пароли дают одинаковые хеши:

```
1|alice|a91f3c...07de
2|bob  |a91f3c...07de   ← пароли совпадают, и это видно
```

Из-за этого:
- видно, у каких пользователей одинаковые пароли;
- один прогон словаря проверяет сразу всю базу;
- можно заранее построить таблицу «пароль → хеш» (по аналогии с радужными таблицами).

### Этап 3. `RandomSaltingAndLoginPage`: случайная соль и вход

**Что сделано:**
- для каждого пользователя генерируется своя 16-байтная соль, которая хранится в базе рядом с хешем;
- добавлена страница входа `/login` с проверкой пароля.

**Как работает проверка:** хеш нельзя расшифровать, поэтому вычисление повторяется:

```
Регистрация: пароль + случайная_соль → Argon2id → хеш  → в БД (соль, хеш)
Вход:        ввод + соль_из_БД      → Argon2id → хеш' → сравнить хеш' и хеш
```

**Меры защиты:**

| Мера | Зачем |
|---|---|
| Уникальная случайная соль | одинаковые пароли дают разные хеши; атакующий вынужден перебирать **каждого пользователя отдельно**; предвычисленные таблицы бесполезны |
| `crypto/rand` вместо `math/rand` | значения `math/rand` предсказуемы; для солей, токенов и ключей нужен криптографически стойкий генератор |
| `subtle.ConstantTimeCompare` вместо `==` | сравнение за постоянное время защищает от **timing-атак** |
| Одно сообщение «Неверный логин или пароль» для обоих случаев | форма входа не подсказывает, какие логины существуют (**user enumeration**) |
| Фиктивное хеширование для несуществующего пользователя | время ответа одинаковое, поэтому существование логина нельзя определить и **по времени** |

**Оставшаяся уязвимость:** соль не секрет и лежит в базе. При утечке базы у атакующего есть всё для перебора: соль, хеш и параметры. Перебор медленный, но слабые пароли вроде `qwerty123` всё равно найдутся.

### Этап 4. `Peppering`: секретный pepper

**Что сделано:** перед Argon2id пароль пропускается через **HMAC-SHA256** с секретным ключом (pepper), который **не хранится в базе**, а передаётся через переменную окружения.

```
HMAC-SHA256(pepper, пароль) + соль → Argon2id → хеш
```

```go
func applyPepper(password string) []byte {
	mac := hmac.New(sha256.New, pepper)
	mac.Write([]byte(password))
	return mac.Sum(nil)
}
```

Если утекла только база, атакующий не может даже **начать** перебор: каждый пробный пароль нужно сначала пропустить через HMAC с неизвестным 256-битным секретом.

**Меры защиты:**

| Мера | Зачем |
|---|---|
| Pepper хранится вне БД (переменная окружения) | утечки одной только базы недостаточно для перебора |
| HMAC, а не склейка `пароль + pepper` | криптографически корректная конструкция «хеш с ключом»; на выходе всегда 32 байта, что важно, например, для bcrypt с его лимитом в 72 байта |
| **Fail closed:** без `PEPPER` сервер не запускается | нет «значения по умолчанию», которое незаметно попадёт в продакшен |
| Проверка длины pepper (≥ 32 байт) и формата base64 | защита от слабого или случайно обрезанного секрета |

## Итог

| Этап | Что хранится в БД | Последствия утечки базы |
|---|---|---|
| 1. Открытый текст | `qwerty123` | пароли сразу известны |
| 2. Argon2id + общая соль | одинаковые хеши у одинаковых паролей | один перебор работает сразу на всех |
| 3. Argon2id + случайная соль | уникальные хеши | медленный перебор по каждому пользователю отдельно |
| 4. + pepper | уникальные хеши, секрет вне БД | без pepper перебор невозможен |

## Запуск

Требуется Go 1.21+.

```bash
git clone <url-репозитория>
cd HMAC
go mod download
```

Этапы 1–3:

```bash
cd passwords/typicalVulnSite        # или slowHashFunction, RandomSaltingAndLoginPage
go run .
```

Этап 4 (нужен pepper):

```bash
cd passwords/Peppering
export PEPPER=$(openssl rand -base64 32)
go run .
```

Страницы:
- регистрация: http://localhost:8080/register
- вход: http://localhost:8080/login (с этапа 3)

Посмотреть содержимое базы:

```bash
sqlite3 users.db "SELECT * FROM users;"
```

> При переходе между этапами удаляй `users.db`: структура таблицы и формат хешей меняются.

### Эксперименты

- **Обход клиентской валидации:** `curl -X POST -d "username=test&password=1" http://localhost:8080/register`. На этапе 1 без серверной проверки такой пароль был бы принят.
- **Одинаковые пароли:** зарегистрируй двух пользователей с одним паролем на этапах 2 и 3 и сравни хеши.
- **Роль pepper:** на этапе 4 зарегистрируйся, перезапусти сервер с другим `PEPPER` и попробуй войти. Вход не пройдёт, хотя пароль верный.

# Подпись вебхуков через HMAC-SHA256

Учебный AppSec-проект: уязвимый и исправленный получатель вебхуков на Go.

Вебхук — это входящий HTTP-запрос от внешнего сервиса (GitHub, платёжной системы) о каком-то событии. Адрес получателя публичный, и отправить на него запрос может кто угодно. Поэтому отправитель подписывает тело запроса общим секретом, а получатель проверяет подпись. Так он убеждается, что запрос прислал тот, у кого есть секрет, и что тело никто не изменил по дороге.

> ⚠️ Папка `vulnerable/` уязвима намеренно. Не используй её код в реальных приложениях.

## Стек

Только стандартная библиотека Go: `net/http`, `crypto/hmac`, `crypto/sha256`, `encoding/json`.

## Структура

```
webhook/
├── sender/main.go      # отправитель: подписывает событие и отправляет его
├── vulnerable/main.go  # уязвимый получатель (порт 9001)
├── fixed/main.go       # исправленный получатель (порт 9002)
└── README.md
```

## Схема подписи

Отправитель кладёт в заголовки метку времени и подпись:

```
POST /webhook
X-Timestamp: 1762613538
X-Signature: sha256=5d61c4...e9a0

{"id":"evt_6b7f38327d265bc7","type":"user.registered","username":"alice"}
```

```
подпись = HMAC-SHA256(secret, timestamp + "." + сырое_тело)
```

Получатель повторяет то же вычисление по полученным байтам и сравнивает результат с заголовком. Если подписи совпали, запрос настоящий.

## Уязвимый получатель (`vulnerable/`)

| # | Ошибка | Чем опасна |
|---|---|---|
| 1 | Подпись `sha256(secret + body)` вместо HMAC | **Атака удлинением сообщения:** по известной подписи можно, не зная секрета, посчитать подпись для `body + padding + свои_данные`. Здесь атаке мешает разбор JSON (padding ломает синтаксис), но в форматах вроде query-строк она работает |
| 2 | Сравнение подписи через `==` | **Timing-атака:** сравнение заканчивается на первом несовпавшем символе, и по времени ответа можно побайтово подобрать подпись к поддельному телу |
| 3 | Подпись проверяется по **заново собранному JSON**, а не по сырому телу | Разные байты превращаются в одну и ту же структуру: лишние поля отбрасываются, пробелы и регистр ключей не важны. Подписано одно, а в журнал и дальше по цепочке уходит другое |
| 4 | Нет метки времени и ID события | **Replay:** перехваченный валидный запрос можно отправлять снова и снова |

Плюс нет ограничения размера тела: можно прислать запрос на гигабайт.

## Исправленный получатель (`fixed/`)

Порядок проверок имеет значение:

1. **Сырое тело** читается через `io.ReadAll` с `http.MaxBytesReader` (до 1 МБ).
2. **Timestamp** должен быть не старше 5 минут.
3. **HMAC-SHA256** считается именно по этим байтам вместе с timestamp. Метка времени входит в подпись, иначе её можно было бы просто подменить на свежую.
4. **`hmac.Equal`** сравнивает подписи за постоянное время.
5. **Только теперь** разбирается JSON.
6. **ID события** проверяется на повтор. Это делается после проверки подписи, иначе атакующий мог бы заранее «занять» чужие ID поддельными запросами.

| Мера | Что закрывает |
|---|---|
| HMAC вместо `sha256(secret + body)` | атаку удлинением сообщения |
| `hmac.Equal` вместо `==` | timing-атаку |
| Проверка по сырым байтам, JSON после подписи | подмену содержимого, которое не участвовало в подписи |
| `http.MaxBytesReader` | DoS огромным телом |
| Timestamp в подписи + окно 5 минут | replay старых запросов |
| Уникальный ID события | replay внутри 5-минутного окна |

ID хранятся в памяти, этого достаточно для обучения. В реальном сервисе нужны БД или Redis с TTL. Хранить ID дольше окна в 5 минут не требуется: более старые запросы и так отсекает проверка timestamp.

## Запуск

Требуется Go 1.21+. Сгенерируй общий секрет и задай его **в каждом терминале**:

```bash
export WEBHOOK_SECRET=$(openssl rand -hex 32)   # в первом терминале
echo $WEBHOOK_SECRET                             # скопируй и задай так же в остальных
```

```bash
# Терминал 1
go run ./vulnerable

# Терминал 2
go run ./fixed

# Терминал 3: отправка
go run ./sender -target vulnerable
go run ./sender -target fixed
```

Флаги отправителя:

| Флаг | По умолчанию | Назначение |
|---|---|---|
| `-target` | `fixed` | `vulnerable` (порт 9001) или `fixed` (порт 9002) |
| `-user` | `alice` | имя пользователя в событии |
| `-type` | `user.registered` | тип события |
| `-age` | `0` | «состарить» timestamp, например `-age 10m` |

После отправки `sender` печатает готовую `curl`-команду с теми же заголовками и телом. Она нужна для экспериментов ниже.

## Эксперименты

Сначала отправь событие (`go run ./sender -target ...`) и скопируй напечатанную `curl`-команду.

**1. Повтор запроса (replay).** Выполни `curl`-команду ещё раз без изменений.

**2. Изменение одного байта.** В `--data-binary` замени `alice` на `alicf`.

**3. Лишнее поле.** Добавь в конец JSON `,"role":"admin"` перед закрывающей `}`.

**4. Без подписи.** Удали строку с `X-Signature`.

**5. Подмена timestamp.** Замени значение `X-Timestamp` на другое число.

**6. Старый запрос.** `go run ./sender -target ... -age 10m`.

### Результаты

| Эксперимент | `vulnerable` | `fixed` |
|---|---|---|
| Обычный запрос | ✅ `200 ok` | ✅ `200 ok` |
| 1. Повтор того же запроса | ❌ `200 ok`, событие обработано второй раз | ✅ `401 duplicate event` |
| 2. Изменён один байт тела | ✅ `401 invalid signature` | ✅ `401 invalid signature` |
| 3. Добавлено поле `"role":"admin"` | ❌ `200 ok`, в журнал записано тело с `role` | ✅ `401 invalid signature` |
| 4. Без подписи | ✅ `401 invalid signature` | ✅ `401 missing signature` |
| 5. Подменён timestamp | — (timestamp не проверяется) | ✅ `401 invalid signature` (или `timestamp expired`, если время вне окна) |
| 6. Запрос 10-минутной давности | ❌ `200 ok` | ✅ `401 timestamp expired` |

Эксперимент 3 показывает ошибку 3: уязвимый получатель проверил подпись по пересобранной структуре, где поля `role` нет, и подпись сошлась. Но в журнал записано **сырое** тело, которое подписано не было. Любой сервис дальше по цепочке, который читает сырой payload, увидит `"role":"admin"`.
